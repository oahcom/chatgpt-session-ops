## 2. §6.2 — T1–T5 取舍裁定

<text color="secondary" size="xs">逐项裁决</text>

| 项目 | 裁决 | 理由 |
|---|---|---|
| T1 留存失败只 WARN | 必须修改 | 全量留存承诺不能容忍静默丢失 |
| T2 logs 不入库 | 接受 | 私密数据不应进入公开仓库 |
| T3 追加写不加锁 | 必须修改 | 串行编排不等于跨进程互斥 |
| T4 非法 ID 归 unassigned | 必须修改 | 混合不同会话，破坏隔离 |
| T5 异常 status=null | 接受 | 状态语义合理 |

### T1 — 留存失败只 WARN

<badge color="danger">必须修改</badge>

这里需要区分两个不同的故障：

**A. 发送之前，prompt 无法留存。**

如果继续发送，意味着用户要求留存的内容已经被使用，却没有任何留存记录。

这是可预防的数据丢失。

我不接受单纯 WARN 后继续投递。

应当：

- prompt 写入失败时，禁止开始发送；
- 或者先成功写入一个可靠的本地持久化队列，再允许发送；
- 不得将未持久化的 prompt 发送出去。

**B. 发送之后，reply 无法留存。**

此时不能撤销已经发生的交互。

应当：

- 明确标记日志未完成；
- 保留已经持久化的 prompt；
- 进入可恢复的待补写状态；
- 明确报告回复留存失败；
- 不得将这轮交互显示为完整留存成功。

目前的：

```python
try:
    _log_turn(...)
except Exception:
    print("WARN: 会话日志留存失败…")
```

不能满足这个要求。

问题不在于 WARN 本身，而在于 WARN 之后没有可靠的恢复机制，也没有可查询的失败状态。

**裁决：发送不应因日志故障而造成新的不可恢复问题，但也不能把日志失败当成无关紧要的非关键错误。**

### T2 — logs 不入库

<badge color="success">接受</badge>

这是合理取舍。

理由：

- 仓库公开；
- prompt 和 reply 包含私密对话；
- `.gitignore` 排除 `logs/` 是正确的；
- 用户要求的是项目内留存，不等于必须提交到 Git。

这里采用一个重要的项目事实：

B 是唯一正式权威源，A 是 WorkBuddy Skill 运行副本，正式内容由 B 同步至 A。不能仅因为 A/B 文件不同步就直接认定架构错误。<MemoryCite />

因此：

**不要求将私人日志提交到 Git，也不要求把日志文件放进公开仓库。**

但必须保证：

- 日志属于项目的持久化运行数据；
- 不随代码更新或安装覆盖而意外删除；
- 有明确的数据保留位置；
- 用户可以定位和检索这些日志。

当前 `BASE/logs/conversations/` 可以作为实现基础，但需要明确其生命周期。

### T3 — 不加锁

<badge color="danger">必须修改</badge>

理由：

```text
同一会话串行
```

不等于：

```text
同一会话永远不存在跨进程并发
```

可能的场景：

- 两个自动化实例同时操作同一会话；
- 一个普通发送和一个 P1 续接同时操作；
- 重复启动的 WorkBuddy 任务；
- 测试和实际运行同时操作同一日志。

`open(path, "a")` 并不能给你提供完整 JSONL 记录级别的跨平台、跨进程原子性保证。

尤其是大回复可能达到数万字符。

要求：

- 对同一会话日志文件实施跨进程互斥；
- 锁覆盖完整记录追加；
- 写入失败必须能被识别；
- 不得因为并发写入产生无法解析的记录。

这里不要求全局锁。

**按会话文件加锁即可，不同会话之间仍然可以并行。**

### T4 — 非法 conv_id 归入 `_unassigned.jsonl`

<badge color="danger">必须修改</badge>

当前实现：

```python
if not _ID_RE.match(cid):
    cid = "_unassigned"
```

存在两个问题。

第一，多个不同的未知会话会被合并。

第二，无法区分：

- 新建会话尚未获得 ID；
- 已有会话 ID 格式不符合规则；
- CDP 提取 ID 失败；
- 上游返回异常；
- 真正的匿名交互。

这些不是同一种情况。

项目此前已有明确的身份治理要求：未知 canonical identity 应 fail-closed，不能通过猜测或隐式归并解决。这里应保持同一原则。

要求：

1. 已知会话 ID 必须严格归入对应文件。
2. 新会话允许有明确的临时身份，待取得真实 ID 后关联。
3. 未知身份不得伪装成某个真实会话。
4. 不同未知会话不得全部混入一个无法区分的文件。
5. 保留原始 ID 和身份解析失败原因。

可以使用独立的未分配记录或临时轮次标识，但必须能够追踪每一轮的真实来源。

### T5 — 异常轮次 status=null

<badge color="success">接受</badge>

这是合理的设计。

三种情况应当明确区分：

| 状态 | 含义 |
|---|---|
| `status=null` | 执行未正常完成，发生异常 |
| `status=1` | 执行完成，但业务结果失败 |
| `status=200` | HTTP 请求成功 |

需要强调：

HTTP 200 不等于完整回复成功留存。

因此，接受 T5 的同时，要求增加独立的回复留存状态，不能只依靠 HTTP status 判断日志完整性。

## 3. §6.3 — `_last_reply_text` 隐式状态可靠性

<badge color="warning">需要补强</badge>

目前的方案：

```python
self._last_reply_text = text or ""
```

外层：

```python
reply = getattr(api, "_last_reply_text", "")
```

优点：

- 改动较小；
- 能够复用 `save_reply` 已经提取的正文；
- 不需要重新解析回复文件；
- 不改变正常发送结果。

但它存在一个语义缺陷。

### 空字符串不代表没有回复

以下情况目前可能都表现为：

```json
{
  "reply": ""
}
```

实际却完全不同：

1. 没有获得回复。
2. 收到了空回复。
3. SSE 解析失败。
4. HTTP 413。
5. HTTP 非 200。
6. 回复已取得，但保存失败。
7. P1 通道根本没有调用 `save_reply`。
8. 回复提取只取得了部分正文。

这些情况不能混为一谈。

### 必须增加显式状态

建议增加：

```json
{
  "reply": "",
  "reply_state": "unavailable",
  "reply_error": "..."
}
```

建议状态至少覆盖：

| 状态 | 语义 |
|---|---|
| `captured` | 完整正文已捕获 |
| `empty` | 明确捕获到空回复 |
| `unavailable` | 未取得回复 |
| `partial` | 仅取得部分回复 |
| `capture_failed` | 回复提取失败 |

实际字段名可以调整，但语义必须存在。

另外，建议将实例属性初始化为：

```python
self._last_reply_text = None
```

每轮开始重置。

这样可以区分：

- `None`：没有捕获到正文；
- `""`：明确捕获到空正文；
- 非空字符串：捕获到了正文。

**特别注意：不要将上一轮回复残留到下一轮。**

目前外层重置 `_last_reply_text` 的做法是正确方向，但需要将状态与正文一起管理。

## 6. §6.6 — 其他遗漏的失败模式

以下是我认为需要补充审查的具体问题。

### F3 — prompt 可能不是实际发送的原文

<badge color="warning">必须核实</badge>

目前 `_log_turn` 接收 `prompt_file`，并且记录：

```python
"prompt": ptext
```

需要确认 `ptext` 是：

- 实际发送时读取的字符串；
- 还是发送结束后重新读取 prompt 文件得到的字符串。

如果是后者，存在一个具体问题：

```text
T1: 读取 prompt.txt 并发送
T2: prompt.txt 被修改
T3: _log_turn 再次读取 prompt.txt
```

日志记录的就不再是实际发送的内容。

要求：

在真正发送之前取得本轮实际使用的 prompt 字符串，并将同一份不可变数据传给日志记录流程。

验收：修改或删除原始 prompt 文件，不得改变已经发送轮次的日志正文。

### F4 — 回复正文与 reply_file 的一致性

需要验证：

```json
{
  "reply": "...",
  "reply_file": "replies/..."
}
```

是否始终指向同一轮、同一份完整回复。

特别需要测试：

- 回复文件保存成功，但日志失败；
- 日志成功，但回复文件保存失败；
- 回复文件已存在，被覆盖；
- 隔离路径与正常路径；
- 同一秒发生多轮操作。

不能让 `reply_file` 指向另一轮回复。

### F5 — 文件写入的部分失败

目前：

```python
f.write(line)
f.flush()
os.fsync(f.fileno())
```

虽然调用了 `fsync`，但 `fsync` 的 `OSError` 被吞掉。

这意味着程序可能把记录视为成功，实际却没有获得预期的持久化确认。

要求：

- 区分写入失败和持久化确认失败；
- 对失败记录保持明确的未完成状态；
- 不得把持久化失败伪装为成功留存。

这里不要求引入复杂事务数据库。

### F6 — 会话 ID 正则表达式的合法性

需要核实 `_ID_RE` 是否覆盖所有真实合法的 conversation ID。

不能只用 UUID 样例证明合法。

如果上游将来返回合法但格式不同的 ID，当前实现会将多个真实会话错误合并。

验收要求：

使用项目中所有实际支持的会话 ID 类型进行测试；非法输入不能逃逸目录，也不能与其他真实会话合并。

### F7 — 自动化只读白名单的边界

三个 CLI 命令加入 `READONLY_ARGV` 是正确方向。

但是需要验证：

- `--log-search` 不创建或修改文件；
- `--log-list` 不改变日志；
- `--log-show` 不改变日志；
- JSON 输出不会意外执行其他操作；
- 参数缺失或错误时不会落入普通发送分支。

尤其不能只验证正常参数。

### F8 — 敏感数据保护

由于现在是完整 prompt 和 reply 留存，日志已经成为敏感数据存储。

至少需要确认：

- 文件权限不会默认开放给其他普通用户；
- 不会跟随符号链接意外写入项目外部；
- 搜索输出不将完整私人内容写入额外的公共日志；
- 备份与安装清理策略不会误删或泄漏日志。

这里不要求加密整个日志系统，但必须有明确的访问控制和生命周期。

# 9. 最终验收原则

这次返修完成后，我不会只根据测试数量或者 CI 状态判断通过。

需要满足以下四项：

**第一：入口完整性。**

所有正式投递通道都必须进入日志体系，特别是 P1 CDP。

**第二：数据完整性。**

实际发送的 prompt 与实际取得的 reply 必须对应同一轮交互，不能以空字符串掩盖缺失。

**第三：会话隔离。**

不同会话不能混合，未知身份不能靠归并来掩盖身份解析失败。

**第四：故障可见性。**

磁盘满、权限错误、并发冲突、回复提取失败、测试污染，都必须有明确且可验证的处理结果。
